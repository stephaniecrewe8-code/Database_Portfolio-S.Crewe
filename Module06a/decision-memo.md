# Decision memo to Lea Winter and Yasmin Kaya

Keep operational job ingestion, transactional updates and point lookups in SQLite because these are small, frequent OLTP operations. Move the historical reporting copy to Parquet and query it with DuckDB because the dashboard and monthly reports scan and aggregate a large history dataset. In my benchmark, the dashboard query took [SQLite median] ms in SQLite and [DuckDB median] ms in DuckDB; the monthly query took [SQLite median] ms and [DuckDB median] ms, respectively. The Parquet file occupied [Parquet bytes] bytes, compared with [history.db bytes] bytes for the SQLite history database.

I recommend rebuilding the Parquet snapshot after the operational shift closes each night, once the day's ingestion has completed. A scheduled refresh job should be owned by the data/application operations role, write to a temporary file, verify row count and rounded `SUM(part_price)`, and replace the published Parquet file only after the checks pass. The dashboard should display the last successful refresh timestamp and flag the report as stale when the expected refresh window is missed. A stale report can mislead management even if it runs quickly, so freshness must be visible and refresh failures must alert the owner. Frequent single-row updates and transactional ingestion should not move to Parquet because it is an analytical snapshot, not the operational source of truth.

The `--check` step protects against missing or extra rows and many changes to aggregate prices, but matching row counts and totals are not a cryptographic checksum and can miss compensating row-level changes.
